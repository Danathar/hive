- The backend smoke's pinned lane runs again, and a runner fault no longer gets reported as broken contributor CLIs ([#5883](https://github.com/hivecommons/hive/issues/5883)). Moving the workflow to the self-hosted fleet ([#5862](https://github.com/hivecommons/hive/pull/5862)) kept the image-heavy jobs on hosted runners but missed that the pinned lane is image-heavy by definition — it runs the suite *inside* `ghcr.io/hivecommons/hive-contributor`, so it needs podman, and the fleet image has none. Every scheduled run died at the image pull in about seven seconds with `podman: command not found`, so the CLI versions hive ships have been unverified since. The pinned lane now runs on `ubuntu-latest` while the latest lane stays on the fleet, keeping the queue relief that motivated the move; a preflight step names a missing container engine outright instead of exiting 127, and writes that into the evidence artifact so it is not empty. The failure-issue job also stopped guessing: it filed "[Backend smoke: pinned] … the CLI versions hive SHIPS in the contributor image failed the smoke — contributors are likely broken right now" about a suite that had never executed, which is a false accusation aimed at the wrong owner. It now checks whether the suite step actually ran, reports a pre-suite failure as an environment fault naming the step that broke, and threads those separately from real CLI failures — the same rule the lane split already follows, since "the shipped CLIs are broken" and "the runner could not start the suite" have different owners and different urgency. That script is JavaScript embedded in a workflow that only executes on a scheduled failure in production, so it had no coverage at all; `bin/test_backend_smoke_attribution.sh` now extracts it from the workflow and runs it against fixtures built from the real failing run.
