- Agents that cannot start now say why, and the hive stops relaunching them forever ([#5958](https://github.com/hivecommons/hive/issues/5958), from [#5921](https://github.com/hivecommons/hive/issues/5921)). A hive spent 4,025 log lines and a fresh tmux session every ~3 minutes relaunching agents that could not possibly come up: Copilot was not logged in, a bob API key was rejected, and one agent was configured `backend: copilot` but launched by `launch_cmd: bob` — so the readiness probe waited for a prompt the launched binary never prints. All three are ordinary, user-fixable conditions, and none of them reached the operator: the card, the fleet row and the log all said `restart needed` or `hung`, and the fleet page showed the agents green and "able" the whole time. A failed start is now recorded with a stable class and an actionable reason — `copilot: not logged in`, `bob: API key rejected (401)`, `backend/launch_cmd mismatch` — which rides agent state out to the dashboard card, the heartbeat and the fleet verdict. Consecutive failures of the SAME reason escalate a backoff (1m → 5m → 15m → 30m) and, after three, mark the agent blocked: the crash-restart loop and the Copilot hang diagnostic both stand down, and the fleet's `able` count excludes it, so a hive can no longer report agents as able when none of them started. The block is a pause, not a dead end — the 30-minute ceiling keeps re-probing (the fixes here happen out of band, with nothing to notify the hive that a human logged in or pasted a key), and an explicit retry — the dashboard restart button, or the relaunch that follows saving a bob key — clears the backoff outright rather than making an operator wait. The Copilot hang check also now keys on the agent's effective backend instead of its declared one, and reports a `backend`/`launch_cmd` contradiction by name instead of running a diagnostic that cannot converge.
