- The advisory digest no longer re-emits findings computed at an older commit as counted, severity-ranked open items when the finding itself names work that has since closed ([#6080](https://github.com/hivecommons/hive/issues/6080)). In the 2026-09-05 digest two findings were carried forward this way; one was listed open at the exact commit that fixed it, and the other named its own remediation in its own body — an issue and a PR that had been closed and merged roughly 23.5 hours earlier. Both were holding top-10 HIGH slots while other findings went unshown. The digest now asks GitHub whether the work a stale finding names has closed, and moves the finding to Recently Resolved instead of listing it as open. It retires a finding only when every reference it names resolves as closed — a still-open reference or a lookup that fails keeps it open, and a finding computed AT the analyzed commit is never retired, since a report that an issue was closed too early is exactly what a maintainer needs to see. How long ago that work closed decides only whether the retirement is still announced under Recently Resolved, never whether the finding is open: a retirement that expired after 30 days would return the finding to the counted, severity-ranked list permanently, with nothing about it or the work it names having changed. The GitHub lookups are memoized per digest build and capped, so a large digest cannot spend hundreds of sequential calls re-asking about the same issue — and because a rate-limited lookup keeps a finding open, that is also what stops retirement from quietly failing on exactly the digests big enough to need it. The check runs before the top-N cap, so the freed slot goes to a live finding rather than being spent. Cross-repo references in the digest also linked to a `github.com/gh-<owner>` that does not exist: advisory beads carry an external ref of the form `gh-<owner>/<repo>#<n>`, and the `gh-` source prefix was read as part of the owner, so every one of those links was dead. The renderer now strips the prefix, which heals beads already stored that way, and new beads are written without it — the dedup accepts both forms so no duplicate advisory is opened across the change.
